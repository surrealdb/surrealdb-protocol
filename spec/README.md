# SurrealDB wire specification data

Language-neutral data that every SurrealDB SDK should agree with. Everything
here is a plain data file, so an SDK can read it from its own test suite in any
language without depending on code from this repository.

| File | What it is |
|---|---|
| [`cbor-tags.yaml`](cbor-tags.yaml) | The authoritative table of CBOR tags used on the WebSocket and HTTP `/rpc` wire |
| [`vectors/cbor.yaml`](vectors/cbor.yaml) | CBOR test vectors: hex plus the expected value, generated by the server |
| [`vectors/cbor2.yaml`](vectors/cbor2.yaml) | `cbor.2` test vectors: the sized numbers, tagged |
| [`vectors/proto.yaml`](vectors/proto.yaml) | The same values as protobuf `surrealdb.protocol.v1.Value` messages |

## The CBOR tag table

[`cbor-tags.yaml`](cbor-tags.yaml) lists every tag the server knows, with:

- `status`: `active` (the server encodes and decodes it), `refused` (the
  server used to accept it and now refuses it; `use` names the tag to send
  instead), or `reserved` (never encode it; the server refuses it).
- `formats`: the CBOR dialects the tag is valid in, when it is not all of
  them. The sized-number tags 180 to 188 are `cbor.2` only.
- `content`: the shape of the tagged item.
- `notes`: the edge cases that have broken SDKs before: pre-1970 datetimes,
  empty and unsigned durations, record id key types, range bounds, NONE versus
  NULL.

It also covers the three CBOR dialects (`cbor`, `cbor.2` and `shaped`), what
the server's strict decoder refuses (the text-form tags 0, 9 and 13, unknown
tags, integers outside i64, duplicate map keys, tag 6 around anything but
null), the untagged types (integers are i64, floats use the shortest exact
width, map keys must be unique strings) and the values that have no CBOR
encoding at all, such as regex.

The table describes the SurrealDB 4.0 wire. Where a server before 4.0 behaved
differently, the row says so. Every server since 1.5.0 reads tags 12, 37 and
14, so an SDK that sends those in place of 0, 9 and 13 needs no version check.

The table was written from the server's codec,
`surrealdb/core/src/rpc/format/cbor/convert.rs`, on the 4.0 line as of
2026-10-24. When the server's codec changes,
update this file in the same release.

## Value test vectors

[`vectors/cbor.yaml`](vectors/cbor.yaml) holds 187 vectors covering every tag in
the table, including the cases that have broken SDKs: pre-1970 datetimes,
nanosecond precision, durations that are empty or above i64, record ids with
every key type (string, int, array, object, uuid and range), exclusive range
bounds, NONE versus NULL, the largest decimals, every geometry type, sets and
files. Each vector has a `kind`:

| kind | What the SDK must do |
|---|---|
| `canonical` | Decode `cbor` to `value`. Encode `value` to something that decodes back to `value`; encoding to exactly `cbor` is recommended, because `cbor` is the server's own encoding of `surql`. |
| `decode` | Decode `cbor` to `value`. This is input the server accepts but never sends (string-form record ids, non-shortest floats, indefinite lengths, unsorted sets). `canonical` is what the server sends back for it. |
| `reject` | Fail to decode `cbor`. The server rejects these, so an SDK that accepts one is reading garbage as data. |

The vectors describe the SurrealDB 4.0 wire over plain `application/cbor`.
4.0 decodes strictly, so some input that 3.x servers accepted is now a
`reject` vector: the text-form tags 0, 9 and 13, integers outside i64,
duplicate map keys and tag 6 around anything but null. Each of those carries a
`legacy` entry whose `canonical` is what a 3.x server sent back for it, so
the file still checks against 3.x; an SDK must not send any of them to any
server. SurrealDB 4.0's sized numbers (i8 to u64, f16 and f32) appear here
widened, as plain `cbor` sends them, and their tags 180 to 188 as reject
vectors. Both hold for plain `cbor` only, so they say `formats: [cbor]`; the
widened ones also say `since: "4.0"`, because older servers cannot parse their
`surql`.

[`vectors/cbor2.yaml`](vectors/cbor2.yaml) holds the `cbor.2` vectors: the
sized numbers tagged, their ranges and widths, and the inputs `cbor.2` still
refuses. `cbor.2` is plain `cbor` plus those tags, byte for byte, so an SDK
that speaks it runs every `cbor.yaml` vector whose `formats` does not leave
`cbor.2` out through its `cbor.2` codec too, and every `cbor2.yaml` vector.

[`vectors/proto.yaml`](vectors/proto.yaml) repeats every `canonical` vector as a
protobuf `Value`, for SDKs that speak gRPC. An SDK must decode `proto` to
`value`, and should encode `value` to exactly `proto`. A vector with
`proto: null` has no protobuf encoding and its `notes` say why: today that is
only durations above i64::MAX seconds, because protobuf `Duration.seconds` is
signed while SurrealDB durations are not. The sized-number arms (`i8` to `f32`)
have no vectors here yet: the server still sends sized numbers over gRPC
widened, as `int64`, `float64` or `decimal`, so the widened vectors are what it
produces today.

Neither file is written by hand. `bun run vectors:write` starts
`surreal start memory`, runs each vector's `surql` over HTTP `/rpc` (CBOR) and
over gRPC, and slices the server's exact bytes out of each response. It then
checks every vector three ways: the hand-written `value` must equal what the
server's bytes decode to, the bytes must round-trip through the server
unchanged (or, for `reject` vectors, the server must refuse them), and the
reference encoder in `conformance/lib` must reproduce the server's bytes. It
also runs each `cbor.yaml` vector as `cbor.2`, where it must behave the same
unless its `formats` says otherwise, and each `cbor2.yaml` vector as plain
`cbor`, where the server's widening must match the reference encoder's.
`bun run vectors:check` does the same without writing, and CI runs it against
the latest release and nightly. The script tells a 4.0 server from an older
one by whether it answers `Accept: application/cbor; v=2` in kind: a 4.0
server writes every field except `legacy`, an older one only
`legacy.canonical` (any other difference fails the run), and an older one
skips `cbor2.yaml` and the `since: "4.0"` vectors. The current files
were generated with `4.0.0-nightly` (a build from 2026-10-25, the first
with the sized numbers) and with `3.3.4`.

Set `SURREAL_BIN` to choose the `surreal` binary, or `SURREAL_URL` to use a
server that is already running.

### Using the vectors from an SDK

Load the YAML in the SDK's own test suite and, for each vector:

```text
canonical:  assert decode(hex(cbor)) == typed(value)
            assert decode(encode(typed(value))) == typed(value)
            optionally assert encode(typed(value)) == hex(cbor)
decode:     assert decode(hex(cbor)) == typed(value)
reject:     assert decode(hex(cbor)) raises
            (ignore `legacy`: it records old servers, not SDK behaviour)
```

where `typed(value)` converts typed JSON (below) into the SDK's native values.
Compare datetimes and durations at nanosecond precision, sets without regard to
order, objects without regard to key order, and floats so that NaN equals NaN
and -0.0 differs from 0.0. If a native type cannot hold a value (a JavaScript
number and `9223372036854775807`, say), the SDK must document how it represents
that value, and the vector must still pass through that representation.

Copy or vendor the files rather than fetching them at test time, and bump them
when this repository releases.

### Typed JSON

Vectors, conformance scenarios and the conformance driver protocol all write
SurrealDB values the same way. Plain JSON types mean what they say, and every
other type is a single-key object whose key starts with `$`:

| Value | Typed JSON |
|---|---|
| NULL | `null` |
| NONE | `{"$none": null}` |
| bool | `true`, `false` |
| int | `42` when within ±2^53, else `{"$int": "9223372036854775807"}` |
| float | `{"$float": 1.5}`; special values as `"NaN"`, `"Infinity"`, `"-Infinity"`, `"-0"` |
| i8, u8, i16, u16, i32, u32, u64 | `{"$u8": 5}`, and so on: a number when within ±2^53, else a string (`{"$u64": "18446744073709551615"}`) |
| f16, f32 | `{"$f32": 1.5}`, `{"$f16": "NaN"}`: spelled as `$float`, and the kind must hold the value exactly |
| decimal | `{"$decimal": "1.5"}`, normalised: no trailing fractional zeros |
| string | `"text"`, or `{"$string": "..."}` |
| bytes | `{"$bytes": "68656c6c6f"}` (hex) |
| uuid | `{"$uuid": "0189e0a5-1c3d-7abc-8def-0123456789ab"}` (lower case, hyphenated) |
| datetime | `{"$datetime": "2024-02-29T12:34:56.123456789Z"}`: RFC 3339 in UTC, with nine fractional digits when the nanoseconds are not zero |
| duration | `{"$duration": [seconds, nanoseconds]}`, nanoseconds in 0..999999999; seconds is a string when beyond ±2^53, and may be negative only where protobuf carries the value (CBOR's tag 14 is unsigned) |
| array | `[...]`, or `{"$array": [...]}` |
| object | `{...}`, or `{"$object": {...}}` when it would look like a typed value |
| set | `{"$set": [...]}` |
| table | `{"$table": "person"}` |
| record id | `{"$record": {"table": "person", "key": <value>}}`, key being an int, string, uuid, array, object or range |
| range | `{"$range": {"start": {"included": 1}, "end": {"excluded": 5}}}`; `null` for an unbounded side |
| file | `{"$file": {"bucket": "b", "key": "/k"}}` |
| geometry | `{"$geometry": <GeoJSON geometry>}`: `Point`, `LineString`, `Polygon`, `MultiPoint`, `MultiLineString`, `MultiPolygon` or `GeometryCollection` |
| regex | `{"$regex": "a.*"}` (protobuf only) |

An object is a typed value only when it has exactly one key and that key is one
of these names. In YAML, where the parser keeps integers and floats apart, a
bare `1` is an int and a bare `1.0` is a float, so the vector files write floats
as `{$float: ...}` anyway for parsers that do not. JSON parsers lose the
distinction, so anything that prints typed JSON must use `$float` for floats.

The sized kinds exist from SurrealDB 4.0. `cbor.2` carries them, and so do
`value.proto` and `value.fbs`, which give each kind its own arm (`i8` to `f32`;
protobuf has no 8- or 16-bit integers or half float, so those arms hold a wider
field that must stay within the kind). Plain `cbor` and JSON widen them to int,
float or (a u64 above i64::MAX) decimal. A `$u8` and a `5` are different values here even though the server
compares them equal, because an SDK must decode tag 181 to its u8, not its int.

The reference implementation is
[`conformance/lib/value.ts`](../conformance/lib/value.ts).
